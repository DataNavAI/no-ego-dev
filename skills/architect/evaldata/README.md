# Eval data for architect

Static fixture for deterministic evals.

Scenario: LaunchPad Lite is a user-facing SaaS MVP that helps indie founders publish a simple product-launch page and collect signups. The PRD success metrics are launch-page publish rate, share-link clicks, signup conversion, signup-form error rate, and week-one return rate. The existing repo has a Next.js frontend, a small API backend, and no complete analytics setup yet.

Deterministic decisions for this eval: the approved PRD and Guided Single Canvas design are treated as durable inputs; authentication uses the incumbent magic-link provider; persistence uses the incumbent managed Postgres database; the MVP is a single Next.js application plus its small API, not microservices; Render is the preferred low-operations host but must be compared against Vercel and Railway with MVP-cost/rollback/worker tradeoffs; PostHog, Plausible, and a lightweight first-party event table should be compared before recommending the smallest adequate analytics path. Product, engineering/on-call, QA, support, and privacy owners are named roles rather than open decisions.

Hermes single-task `delegate_task` runs in the background automatically; the deprecated `background` argument must not be added. A correct first invocation ends at a durable `REVIEW_PENDING` checkpoint after dispatching a fresh reviewer, but it must identify the exact spec revision/round, block handoff, define the structured technical rubric, and state how the callback resumes disposition, revision, fresh re-review, approval, stall detection, and three-round escalation. It must never fabricate a completed review.

The technical specification may not be self-certified. The architect must save a complete draft and spawn a fresh leaf subagent that loads and uses `technical-design-reviewer`; every round uses a different fresh reviewer. The neutral packet includes the exact spec plus objective PRD/CUJ/repository/deployment/security/cost/operational evidence while excluding architect scratch reasoning, hidden transcripts, preferred architecture, persuasive summaries, and desired verdicts. Review output must use a structured severity-ranked verdict and test integrity across invariants/contracts/data/state/failures/security/migration/rollback, actively compare the simplest viable reuse-based alternative, justify every new moving part in a complexity/redundancy ledger, require concrete automatic tests, and require operability/self-monitoring whose telemetry, alerts, simulated failures, and recovery are themselves testable and fail closed. The architect must disposition findings, revise all blocker/high and accepted medium issues, and send the latest revision to another fresh reviewer. It may hand off only with `APPROVED` or `APPROVED_WITH_MINOR_NOTES` and no unresolved blocker/high findings. The revision gate is limited to three rounds with stall detection and user escalation rather than self-approval.

Human review requirement: once the independent technical review has produced the latest material spec revision, the architect must use `reviewable-artifacts` to present canonical Markdown in an explicitly marked `REVIEW_ONLY`/`[REVIEW ONLY — DO NOT MERGE]` rendered draft GitHub PR with a `review-only/*` branch, body warning, available labels, cleanup owner/trigger, stable `DEC-*`, `API-*`, `DATA-*`, and `RISK-*` anchors, diagrams, exact decisions requested, and a disposition log. It must process inline human comments against the latest revision and block coder/project-manager handoff on unresolved material architecture decisions. After preserving the accepted spec at its canonical destination, it must close the review PR without merge and verify cleanup of temporary branch/worktree/preview/access/scratch resources.

A good architect response should create a durable tech-spec artifact, choose or recommend maintainable hosting, and add a product-metrics instrumentation plan. The metrics plan should define event names/properties and capture points for create page → publish → share link → signup, API success/failure events for signup errors, an analytics/dashboard destination, privacy constraints for user/session IDs, ownership/review cadence, and QA/tests proving events fire once and do not include sensitive payloads. Missing analytics infrastructure should become explicit implementation work rather than a vague future TODO.

The task breakdown should also end every milestone or feature with a scheduled refactoring task. That task should target the LaunchPad Lite areas most likely to accumulate coupling or duplicate code, such as editor/publish/share/signup flows, analytics event emission, API validation/error handling, and dashboard/reporting glue. Acceptance criteria should require reduced complex dependencies, removal of redundant product logic, clearer test seams/fixtures, and automated tests that verify the touched product features and CUJs without relying only on manual QA.
