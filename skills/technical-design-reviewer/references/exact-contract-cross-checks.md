# Exact implementation-contract cross-checks

Use these probes when a design candidate includes executable workflow, infrastructure, packaging, API, or deployment contracts. They generalize failures found in immutable static/serverless candidates.

## Producer/consumer closure

For every generated value, compare the producer with every consumer rather than validating each file independently:

- artifact key generated by the build/deploy script versus CloudFormation `AllowedPattern`;
- ZIP layout and exported handler versus Lambda `Handler`;
- package digest encoding (hex versus base64) versus `CodeSha256` and parameter regex;
- release/count/schema values derived from immutable input versus hard-coded Lambda environment values;
- workflow inputs and parameter overrides versus every required template parameter;
- template outputs versus every name consumed by deployment, verification, restore, and rollback scripts;
- public `version.json` fields versus the exact authoritative contract (including deliberately deterministic or omitted timestamps);
- deployable manifest claims versus the generated tree: every regular file represented exactly once with digest, byte count and media type when promised;
- cache-control and invalidation declarations versus the actual per-path upload commands;
- digest-addressed S3 keys versus uploader behavior: an immutable-looking key is not write-once if unconditional upload can replace existing bytes;
- alarm names/outputs versus every verifier, runbook and configured-state readback consumer.

Run one deterministic fixture through both sides. Escaping errors in YAML/regex and digest-format mismatches often survive syntax validation.

## Shared artifact and entry-point closure

When multiple Lambdas/functions share one bundle or entry point:

1. Enumerate module-load validation and initialization before handler dispatch.
2. Build a complete environment-variable matrix per function.
3. Smoke-import and invoke each event shape separately from the built artifact.
4. Verify each execution role can perform only that entry point's calls.

A scheduled branch inside a shared runtime is not viable if common module initialization requires API-only environment or permissions.

## State-contract triangulation

For every user-visible state, compare:

- product meaning and precedence;
- technical reducer inputs and transition rule;
- serialized schema representation;
- runtime overlay behavior;
- UI copy/instrumentation;
- tests for every state and precedence collision.

Flag a state as unrepresentable when two states share the same trigger, when prose says a value is derived but no exact derivation exists, or when schema accepts combinations the validator claims are impossible.

An objective technical producer is not sufficient when it changes the approved product meaning. Cross-check the producer against the exact product condition, not merely the state label. If product prose defines a state by record count while the design introduces a separate connection/review bit, exercise zero-record combinations against both contracts and require either semantic agreement or an independently approved product revision.

When a producer depends on reviewed or signed private input, verify authorization closure as well as JSON representability:

- the governing review/signature schema permits the proposed record class;
- record ID, substantive digest, release binding, reviewer identity, and outcome are exact;
- the compiler consumes the same signed bytes the reviewer authorized;
- a new private record type is not smuggled past a closed product enum as an “implementation detail.”

A field can be representable in the target public schema yet still be unauthorized or semantically contradictory upstream.

## Deployment-order simulation

Read the deploy script in actual execution order and simulate both first deployment and update:

- resource/prefix existence before origin switch;
- candidate health persistence before promotion;
- API expand before old/new static overlap;
- cache-control and invalidation paths against the spec;
- convergence checks before pointer/alias movement;
- rollback using retained immutable bytes and versions without rebuilding.

Do not infer safe ordering from section headings or CloudFormation resource presence. The commands must enforce it.

### Phase expressibility and bootstrap closure

Before accepting a prose deployment sequence, prove that the declared infrastructure parameters and resources can express every phase independently:

1. Build a producer/consumer map for each identity or pointer parameter (source revision, API artifact/version, accepted release IDs, static origin prefix, aliases, distribution configuration, persisted release state).
2. For each phase, hold all forbidden-to-move consumers constant and vary only the intended pointer. A single parameter that simultaneously drives API aliases and a static origin cannot implement “expand API while static remains current.”
3. Identify the source of truth after every phase. Reject a design that requires out-of-band resource mutation which leaves the declared template or release-state file in unexplained drift.
4. Simulate initial creation separately from update. If immutable static bytes must exist before stack creation, verify that their bucket/prefix is bootstrap-owned or already exists; a bucket created by that same stack cannot receive pre-stack uploads.
5. Simulate failure after every state-changing step and prove which public pointer remains authoritative, how retries resume idempotently, and how rollback restores both declared and actual state without rebuilding.

Independent API/static parameters prove phase expressibility, not recovery closure. If rollback depends on a persisted release-state file or record, require its exact durable location, closed/versioned shape, owner and ACL, generation/CAS token, retention, and reconciliation rule against actual stack, alias, origin, distribution ETag, and immutable artifacts. Explicitly inject failure after public convergence but before the release-state write: the design must say how stale recorded state is detected, which live pointer wins, and how retry or rollback resumes without guessing.

Treat an impossible phase as a design contradiction even when all scripts are honestly labeled `BUILD_REQUIRED`: future code cannot implement a state transition the parameter/resource model cannot represent.

### Exact hashed-contract semantic closure

When a design cites an exact schema, workflow, template, or script hash as executable evidence, verify both byte identity and semantic content:

- compute/confirm the cited hash;
- inspect whether the exact file contains every field, enum, route, transition, or output attributed to it;
- follow the producer and consumer to confirm they emit and consume the same contract;
- compare the claim's evidence status (`CURRENT`, partial, or future) with repository reality.

A correct hash pointing to an older semantic contract is stronger contradiction evidence, not validation. If the design introduces a future field but cites the old exact schema and current tests as proof, require either a new frozen contract or honest `BUILD_REQUIRED` labeling. Do not require the future implementation merely because it is absent; object only to semantic ambiguity or false current evidence.

### Attestation and protected-approval closure

A checked-in attestation can bind exact product/review bytes while its generic validator still accepts a coordinated replacement of every self-declared identity. Test both layers:

1. Confirm the exact checked-in attestation names the approved revision, candidate manifest/count, review paths/digests, trust anchor, and non-promotion status, and recompute every referenced digest.
2. Mutate the product revision, candidate digest/count, and both review files/digests together while holding only the genuinely external trust inputs fixed. Record whether the validator accepts.
3. If coordinated drift is accepted, identify the separate authority that prevents unauthorized deployment—such as a protected environment variable containing the exact approved full source SHA—and verify the workflow cannot write or bypass it.
4. Do not call generic shape validation an external pin. Either require protected expected product/report digests as validator inputs, or state explicitly that full-SHA human/environment approval is the authorization boundary.
5. Cross-check every workflow path supplies the protected values required by the deployment script; an exact script that always fails because one required environment value is omitted is not executable evidence.

### Finding-disposition truth

For every claimed prior-finding disposition, inspect the actual current artifact named by the disposition. A table saying “runbook corrected,” “workflow replaced,” or “schema frozen” is not evidence when the runbook/workflow/schema still contains the stale authority. Classify the underlying impact (often a handoff-quality LOW, but higher when the stale path can execute or authorize) and never convert an asserted disposition into closure without byte-level verification.

## Executable-CI integrity

Treat a zero-test successful exit as failure evidence when tests are required. Verify imported modules, globs, scripts, fixtures, and evidence-upload paths exist before accepting a workflow. Execute safe commands in a disposable immutable snapshot and report test counts, not only exit status. A table entry containing a literal ellipsis, placeholder argument, or nonexistent script is not an exact executable command; classify it as future work or false executability according to the gate. Also verify that claimed immutable evidence is actually uploaded on failure rather than merely printed to an ephemeral job log.
