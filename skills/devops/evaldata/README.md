# Eval data for devops

Static fixture for deterministic evals.

Scenario: LaunchPad Lite is a new user-facing SaaS MVP. The repo exists, but no hosting provider has been chosen yet. The app is a Next.js frontend with a small API, Postgres persistence, GitHub repo integration, staging and production requirements, and a custom domain whose DNS is not wired yet. The user is on Telegram/mobile and often cannot access the agent machine directly.

A good devops response should inspect the stack, research and compare 3-5 realistic hosting options for this project, recommend one default with tradeoffs and expected MVP cost/operability, then ask the user to choose before creating a provider account or locking architecture. After the user chooses, it should use the configured primary Google account for provider SSO/account ownership when practical, prefer GitHub/provider CLI/API/OAuth/device-code or collaborator flows, and if user action is required, give a condensed phone/chat-friendly checklist with exact URL, account to select, scopes/role, safe billing/free-tier guidance, and non-secret confirmation to send back. It should still cover CI/CD, staging and production, secrets, deployment runbook, monitoring, rollback, hosting cost visibility, and verification.

Release-gate context: `.projects/launchpad-lite/product/supported-device-interfaces.yaml` marks desktop web and mobile web supported, Android planned, and iOS intentionally unsupported for this release. DevOps must require at least one executable test case and a separate current PASS/evidence row for both supported web interfaces against the exact candidate; it must block promotion/deployment if the registry is missing/malformed/undecided or either supported interface is untested, stale, failed, or blocked.

Repository workflow monitoring scenario: GitHub Actions has active `ci`, `security-scan`, `deploy-staging`, `deploy-production`, and nightly data-maintenance workflows. The monitor should inventory workflow trigger definitions, derive every relevant workflow/event/branch lane, and paginate each lane until its latest completed attempts and preceding success are known, so busy PR/push runs cannot hide infrequent nightly, release, or deploy workflows. It should prefer `workflow_run` events plus a 15-minute reconciliation poll and use read-only run/job inspection before deciding. One `ci` failure is a candidate incident; a second consecutive matching completed attempt on the same branch/event must create one durable fix task, while three continuously red mixed-signature attempts create one `mixed-signature` lane task. A safe rerun that fails with the same signature, a required release/deploy check still red and blocking after 30 minutes, or two consecutive scheduled failures also trips the gate. Repeated polls and subsequent matching runs update the same task rather than creating duplicates. Stable workflow ID/path identity, a stored dedupe key, immediate pre-create search, atomic/idempotent upsert, and atomic state writes prevent concurrent webhook/poll races. Failed, timed-out, or ambiguous repair-task writes remain one pending record per dedupe key; retries first search for a task created despite a lost response, and no task is claimed until returned ID/URL and read-back evidence are verified; every event transition and monitor restart reconciles authoritative remote runs/attempts and open tasks before alerting, rejecting stale or out-of-order webhook events. The latest two relevant completed runs must be failures with no intervening success. Workflow renames preserve state by stable identity, and removed/disabled workflows retain a visibility task until an intentional retirement decision is verified. The task includes workflow/run URLs and IDs, SHAs/events, failed jobs/steps, a normalized redacted signature, impact/severity, evidence-grounded suspected cause or `unknown`, owner, and acceptance requiring the original scenario plus two consecutive normal runs to pass without disabling, skipping, or weakening the workflow. Missing trigger/lane/pagination/auth/run/required-check visibility fails closed and creates or updates one deduplicated access/setup task; unchanged visibility alerts remain silent. Setup verifies contents, Actions, branch-rules, task-tracker, and optional webhook permissions, using least-privilege polling when hook administration is unavailable. Simulate all-green silence, first-failure/no-task, matching and mixed-signature persistence, infrequent lane pagination, distinct attempts, concurrent duplicate suppression, deduplicated visibility outages, stale/out-of-order events, malformed data, and recovery without premature closure. Record monitor cadence, permissions, state path, dedupe key, tracker, notifications, and operating instructions in the deployment/monitoring runbook.

Monitoring request scenario: the user says, "Monitor all deployed services and tell me if anything starts breaking." A good devops response should discover all deployed services/environments from runbooks, provider config, repo manifests, and dashboards; identify backend/API services, workers, databases, queues, and provider-managed dependencies; create a Hermes cronjob scheduled `every 5m`; use a deterministic no-agent watchdog script when possible; and make the healthy path silent by printing nothing when all checks pass. The watchdog should check health endpoints, backend error counts/rates, p95/p99 or timeout latency, CPU and memory above 90%, and database/queue/storage pressure where available. It should alert only on threshold breaches, failed checks, missing critical visibility, or useful recoveries; deduplicate repeated alerts with a state file outside the repo such as `~/.hermes/tmp/<project>-monitor-state.json`; manually verify silent healthy output and simulated failure alerts; list the cronjob after creation; and document cronjob id, schedule, script path, state path, monitored services, thresholds, metric sources, delivery target, and pause/remove/run instructions in `.projects/<project>/runbooks/deployment-and-monitoring.md`.
