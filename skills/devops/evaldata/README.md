# Eval data for devops

Static fixture for deterministic evals.

Scenario: LaunchPad Lite is a new user-facing SaaS MVP. The repo exists, but no hosting provider has been chosen yet. The app is a Next.js frontend with a small API, Postgres persistence, GitHub repo integration, staging and production requirements, and a custom domain whose DNS is not wired yet. The user is on Telegram/mobile and often cannot access the agent machine directly.

A good devops response should inspect the stack, research and compare 3-5 realistic hosting options for this project, recommend one default with tradeoffs and expected MVP cost/operability, then ask the user to choose before creating a provider account or locking architecture. After the user chooses, it should use the configured primary Google account for provider SSO/account ownership when practical, prefer GitHub/provider CLI/API/OAuth/device-code or collaborator flows, and if user action is required, give a condensed phone/chat-friendly checklist with exact URL, account to select, scopes/role, safe billing/free-tier guidance, and non-secret confirmation to send back. It should still cover CI/CD, staging and production, secrets, deployment runbook, monitoring, rollback, hosting cost visibility, and verification.

Release-gate context: `.projects/launchpad-lite/product/supported-device-interfaces.yaml` marks desktop web and mobile web supported, Android planned, and iOS intentionally unsupported for this release. DevOps must require at least one executable test case and a separate current PASS/evidence row for both supported web interfaces against the exact candidate; it must block promotion/deployment if the registry is missing/malformed/undecided or either supported interface is untested, stale, failed, or blocked.

Monitoring request scenario: the user says, "Monitor all deployed services and tell me if anything starts breaking." A good devops response should discover all deployed services/environments from runbooks, provider config, repo manifests, and dashboards; identify backend/API services, workers, databases, queues, and provider-managed dependencies; create a Hermes cronjob named with a short plain-language label such as `LaunchPad Lite uptime watch` while keeping the technical job ID in the runbook, scheduled `every 5m`; use a deterministic no-agent watchdog script when possible; and make the healthy path silent by printing nothing when all checks pass. The watchdog should check health endpoints, backend error counts/rates, the configured p95/p99/timeout alert state, CPU and memory above 90%, and database/queue/storage pressure where available. It should alert only on threshold breaches, failed checks, missing critical visibility, or useful recoveries; deduplicate repeated alerts with a state file outside the repo such as `~/.hermes/tmp/<project>-monitor-state.json`; manually verify silent healthy output and simulated failure alerts; list the cronjob after creation; and document cronjob ID, schedule, script path, state path, monitored services, thresholds, metric sources, delivery target, and pause/remove/run instructions in `.projects/<project>/runbooks/deployment-and-monitoring.md`.

Latency-alert boundary scenario: LaunchPad Lite is already active in production and its checkout API is a core customer journey, but it has no latency SLO or baseline and only a generic uptime monitor. A passing response instruments p50/p95/p99 latency with request-volume, timeout/error, database/downstream, route, environment, and deployment context; creates owned warning and critical production alerts; and does not invent a universal threshold. It records a conservative provisional customer-impact threshold, a task to establish the product latency objective and representative baseline, sustained evaluation windows, minimum-traffic or synthetic-probe safeguards, recovery criteria, and non-paging staging validation. It then generates a safe test alert, proves delivery and acknowledgement at the response destination, links the dashboard/runbook and incident/task path, verifies recovery notification, restores the intended threshold, and records immutable evidence. Until that passes, monitoring remains an operational gap rather than complete.
