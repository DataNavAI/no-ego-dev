# Persisted Journey Event Outbox Review

Use for immutable reviews of analytics or domain events that promise retry, idempotency, or exactly-once logical delivery across reloads and state transitions.

## Core model

Activation and completion events belong to the same persisted state authority as the journey they describe. Persist the full logical envelope and event key before first delivery. A sink response may acknowledge the envelope only after success, and that acknowledgement must itself be persisted. Transient controller-only event keys cannot close ambiguous delivery.

## Adversarial matrix

Test activation and completion separately:

1. **Lost acknowledgement:** make the sink receive the event but report failure; reload from storage and prove retry uses the exact original key.
2. **Post-ack reload:** acknowledge successfully, reload again, and prove no duplicate emission.
3. **Replay and rollover:** fail delivery, replay or cross local-day/version identity, and prove the archived envelope retains the original key until acknowledged.
4. **Immediate replay race:** expose replay while another send is in flight; prove ordering cannot replace state before completion is retained or retried.
5. **Bounded saturation:** fill history with pending envelopes and archive one more attempt. The transition must backpressure/fail closed rather than evict unacknowledged data.
6. **Bounded recovery:** acknowledge one retained envelope, retry the transition, and prove only non-pending metadata is dropped.
7. **Normalization priority:** construct `limit + 1` valid persisted rows with the oldest row carrying a full unresolved envelope and all newer rows carrying acknowledged/key-only metadata. Normalization must inspect the complete accepted window, retain unresolved envelopes first, and bound only metadata. If pending rows exceed capacity—or the input is too large to inspect safely—fail closed without overwriting the raw persisted state.
8. **Duplicate and collision matrix:** do not stop at a key-only shadow. Exercise the full key-location cross-product before re-review: active activation vs active completion; activation vs completion in one history row; older history completion vs newer history activation; active vs history; same-type same-key with different payloads; and same-type key-only metadata vs a full envelope. Event keys are global across event types and locations. Cross-type, cross-payload, or otherwise ambiguous reuse must reject the entire store before delivery or persistence. A same-type key-only legacy duplicate may be deduplicated only when the full pending envelope wins; newest-first selection must never erase retryability.
9. **No sanitize-and-overwrite on ambiguity:** exercise the real controller/storage path, not only the engine normalizer. Snapshot the exact raw serialized state, load an ambiguous collision, and prove the UI fails closed while storage remains byte-for-byte unchanged. A normalizer that drops one conflicting row and then persists the sanitized result has converted hostile ambiguity into permanent event loss.
10. **Cross-reload uniqueness:** seed collision detection from active and archived activation and completion keys, including acknowledged events still attached to the active record. Recreate the controller, force its generic sender to generate an acknowledged activation key for `question_answered`, and require retry to a fresh key or fail-closed rejection. Audit engine and controller key sets separately.
11. **Legacy migration:** normalize old persisted shapes into the current canonical envelope shape and rewrite them; do not leave half-migrated state that only appears canonical in memory.
12. **Persistence failure:** if durable write fails, render an explicit recovery state rather than claiming successful progress or delivery closure. For public browser routes, every top-level unavailable path—including failure before routing or controller construction—must install `robots=noindex` and use CSP-safe listeners.
13. **Route-close cancellation at every await:** block each asynchronous sink boundary independently during open/restored retry, question-event delivery, multi-pending delivery, and replay. Call `close()`, replace the route DOM, then release the sink. The stale operation must return `cancelled`/`false`; controller state must remain closed; replacement DOM and raw persisted bytes must remain exact; and no post-close acknowledgement, persistence, unavailable rendering, or journey rendering may occur. Guard inside the delivery loop both before and immediately after each await—not only in callers—then re-check generation before every post-await engine transition. Catch paths must test cancellation before rendering fallback UI. Include a multi-envelope case so closing between sends cannot acknowledge a later envelope from the stale route.
14. **Stale post-await overwrite:** start overlapping activation, completion, and flush operations with deferred sink results and release them out of order. An acknowledgement must never write the whole pre-await store snapshot. Serialize mutations sharing one injected storage boundary where possible, then reread and normalize current storage after the await and acknowledge only the exact still-pending envelope against that latest state. Prove newer activations and unresolved envelopes remain present during and after every interleaving. Queue rejection must not poison later operations.
15. **Exact sink acknowledgement shape:** only a plain exact data record such as `{ok: true}` may acknowledge an event. Extra keys, inherited/null prototypes, accessors, Proxies or fabricated descriptors, non-booleans, null, and throws must retain the same logical key for retry without invoking hostile getters/traps. Validate the dependency output before any ordinary property read.
16. **Incomplete-journey retention:** an acknowledged activation with no completion is still unresolved journey authority. At capacity, reject/backpressure a new activation rather than evict an incomplete journey; subsequently supplying valid completion evidence for the oldest retained journey must still work. Evict only a journey with both activation and completion envelopes present and durably acknowledged.
17. **Retired-key collision ledger:** if fully resolved journeys may be evicted, move every activation, completion, and external evidence key into a bounded retired-key ledger before removal. Generated keys and incoming evidence keys must be checked against active plus retired locations. Derive the bound from the finite release/cohort model (for example, maximum identities multiplied by keys per identity) rather than truncating collision history. Test reuse of each retired key class after eviction and prove rejection leaves state recoverable.
18. **Identity-targeted completion:** when several activations are retained, resolve completion against the exact validated identity carried by completion evidence, not `at(-1)` or another recency shortcut. Reject an external completion key already bound to another identity. Once completed, accept delivery retries only when the supplied evidence key exactly matches the retained key; a different key must not mutate state or emit another completion.
19. **Coherent hostile-input snapshots:** descriptor validation is not enough if production code later rereads the original object. A stateful `Proxy` can present one artist, key, result band, or nested properties record during validation and a different value during use while every individual descriptor looks valid. Recursively inspect the exact own-data shape, capture each expected descriptor value once into a fresh plain snapshot, validate that snapshot, and use only it afterward. Add top-level and nested stateful-Proxy regressions plus caller-mutation-after-call controls; accessors must invoke zero getters. For cloneable data graphs, perform the recursive descriptor/accessor check first, then use `structuredClone(original)` only as a transparent-Proxy rejection probe; ignore its cloned values and continue with the one-read snapshot so clone traversal cannot become a second identity source. For function-bearing dependencies, browser JavaScript has no general transparent-Proxy detector. If the contract requires raw or wrapping dependency Proxies to fail closed, accept only module-identity-branded adapters created by a factory, reject raw objects and Proxies wrapping branded adapters by private `WeakSet`/`WeakMap` identity, capture each callable once, and preserve one underlying storage identity for the mutation queue. State the factory boundary honestly: browser code cannot prove that the raw object supplied to the trusted adaptation factory was not itself a transparent Proxy, so only already-trusted dependencies may be adapted.
20. **Commit/readback ambiguity:** probe storage whose write commits and whose following read throws or reports a mismatch. A boolean API must not return `false` after state may have committed, because a later instance can flush an event the caller was told failed. Do not use post-write readback to turn a successful synchronous commit into `false`. Prefer a branded adapter with an authoritative one-call commit receipt: exact plain own-data `{ok:true}` means committed, while every other return or throw contractually guarantees no commit. Snapshot that receipt once and reject extras, inherited/null prototypes, accessors, Proxies/stateful Proxies, non-booleans, and false without sending. The browser adapter should return `{ok:true}` only after synchronous `localStorage.setItem` returns normally; a contradictory adapter that commits and reports failure is outside the trusted contract because rollback cannot be inferred. If that guarantee is unavailable, require atomic write/CAS or expose an explicit tri-state (`committed`, `not_committed`, `indeterminate`). Tests must include authoritative commit followed by denied reads, no post-write verification read, denied/no-op writes, malformed receipts, completion and acknowledgement writes, and a documented no-cross-tab-CAS limit.
21. **Cross-context limit:** a module-realm `WeakMap` queue coordinates only callers sharing the exact storage identity in that realm. Distinct wrappers, tabs, workers, and processes still need an injected transaction, lock, or CAS boundary when concurrent mutation is in scope. Latest-store reread narrows stale-acknowledgement overwrites but is not atomic across the final read/write gap; state the residual explicitly and test the strongest supported concurrency model.
22. **Delivery outcome separation:** do not overload one boolean with “generation still current,” “delivery attempted but remains pending/unacknowledged,” and “all pending events durably acknowledged.” Use an enum/result object or equivalent explicit checks, and make every caller intentionally handle all outcomes. A usable journey may remain rendered after analytics delivery failure while Replay/archive/rollover remains prohibited. Add a rejected-send regression proving the completed record and exact original key remain active, then a later accepted retry proving observation occurs once before replacement.
23. **Observation-before-terminal replacement:** a successful sink acknowledgement is not itself permission to archive or replace a terminal journey. Replay/reset/rollover must retain the exact completed record until its completion observer returns primitive `true`; false, throw, or unacknowledged state must leave the same record/key retryable. Gate and assert accepted order explicitly—final ordinary event, shared completion, downstream completion, then new activation—because a correct final snapshot can hide an invalid delivery interleaving.
24. **Generation-owned in-flight references:** every controller-level promise/operation reference belongs to the generation that created it. `open()`, `close()`, route replacement, or identity replacement must synchronously detach obsolete ownership while the old task keeps internal generation checks. A restored completed successor must replay independently even when its predecessor sink/observer never resolves. Release the predecessor after successor progress and prove it cannot persist, render, send, observe, clear successor ownership, or change the successor result. Include duplicate-trigger single-flight coverage in the same matrix.

## Review evidence

Require:

- exact baseline SHA, review-head SHA, and tree;
- focused tests for each matrix row plus the full repository gate;
- remote PR `headRefOid` matching the reviewed SHA;
- concrete event-key traces showing equality after ambiguous retry and absence after acknowledgement;
- file:line evidence for blockers;
- current merge blockers separated from future publication/operational risks.

If the head changes while review is running, the verdict is superseded. Reproduce still-relevant findings on the new head, add regressions where applicable, rerun the full gate, and dispatch a fresh exact-head review. An ancestor verdict is useful evidence but never approval for a descendant SHA.
