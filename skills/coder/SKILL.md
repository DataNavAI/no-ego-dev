## Overview

Implement one focused task per branch. Write tests for the key path, keep the diff small, establish and run project-owned static analysis, request bounded review, merge only after exact-SHA approval, and clean up.

## Risk-weighted review convergence

Use **Risk-weighted review**: prioritize hard-to-reverse or high-consequence changes and omit safely reversible nits. Enforce **first-round completeness**: **Round 1** receives all independently discoverable Critical/Important or otherwise material findings in one complete evidence-backed correction set, **Round 2** verifies dispositions and correction regressions, and **Round 3** is final. Later new feedback is allowed only for remediation changes, genuinely unavailable evidence, or a material issue that could not reasonably have been found earlier, and must state `Why it was not discoverable in round 1: <cause>`. **No round 4** is allowed for the same stable scope; a negative Round 3 keeps the candidate unmerged and routes scope/risk decisions to the owner without waiving exact-SHA approval.

### Prior-round context handoff

Before Round 1, create one neutral, immutable **pre-review summary** covering governing scope, acceptance criteria, intended approach, hard-to-reverse risks, known tradeoffs, open questions, and the planned evidence matrix. Embed its exact closed-schema canonical JSON as `pre_review_summary_artifact`; the authority-bearing gate must parse it, verify lineage and serialization, recompute `pre_review_summary_digest`, and persist the verified bytes before dispatch. Provide that exact artifact to every reviewer in every round. The artifact and digest must remain unchanged throughout the stable lineage; changing either requires an explicitly new lineage. It supplements exact source evidence and never argues for approval or narrows independent review.

For every Round 2 or Round 3 dispatch, pass the fresh reviewer the complete continuity packet, not a persuasive summary:

- all prior candidate/base identities and **all prior exact review reports** plus verified report digests for every authorized bundle in every preceding generation;
- a stable-ID **finding disposition ledger** with `UNRESOLVED`, `RESOLVED`, `SUPERSEDED`, or `OWNER_DECISION`, correction evidence, and ownership;
- a **remediation change map** mapping every prior finding to changed paths/sections and focused verification, with any authorized scope delta called out separately;
- the original governing contract and complete current candidate; and
- a canonical **prior-context digest** binding the exact reports, ledger, and remediation change map supplied to the reviewer.

The controller must reject or block a later-round dispatch when this packet is missing, unverifiable, mismatched to any terminal prior generation, or cumulatively incomplete. It must validate that the returned report reconciles every prior finding ID, contains a **contradiction check**, and separates **New material findings**. Later reviewers must not reopen resolved feedback or demand the opposite correction unless current/new authoritative evidence proves the prior direction wrong; that exception must be labeled `PRIOR_FEEDBACK_CORRECTION` with both statements and decisive evidence. New findings are allowed only for remediation regressions, authorized scope additions, genuinely unavailable evidence, or a material Round-1-undiscoverable defect, and must state `Why it was not discoverable in round 1: <cause>`. Unrelated new findings and reversible preferences are omitted. Never suppress a real material safety/correctness defect merely for consistency. When it was reasonably discoverable earlier but missed, preserve it as a **material process escape** with `MATERIAL_PROCESS_ESCAPE`, keep the gate blocked, and escalate the process failure rather than silently omitting it or treating it as ordinary later-round feedback.

### Canonical round accounting

**One review round is one immutable candidate generation.** One composite independent review covers specification, correctness, security, test honesty, conventions, integration, and operational risk for ordinary candidates. A named non-overlapping specialist may be predeclared only for a hard-to-reverse expertise gap; all authorized bundles **share one candidate generation and round number**. Persist one **review-readiness receipt** keyed by repository/artifact, lineage, round, **candidate SHA, current base SHA, and complete authorized review-bundle manifest**, with each per-bundle outcome. **A corrected candidate advances exactly one round** and invalidates every earlier commit-bound verdict. Before freezing that correction, collect the complete material finding set: a new candidate is inadmissible until every authorized bundle in the prior generation has reached a terminal verdict.

For asynchronous UI/state-machine work that renders Replay, Reset, Navigate, Close, Share, or Retry before acknowledgement/finalization settles, follow [`references/render-before-ack-interleavings.md`](references/render-before-ack-interleavings.md): write a deferred-promise RED test at the render-before-await boundary, assert accepted event order and original-key observation, preserve retry/generation semantics, and serialize competing actions rather than relying on sequential tests.

## Rules

1. Create a dedicated branch/PR for each task.
2. Read the tech spec and relevant code before editing.
3. For UI implementation, read and reference the linked design artifacts before editing: project UI guideline, feature UI brief, design images/mockups, screenshots, or Figma/design-tool files. Do not implement visible UI from the tech spec alone when design artifacts exist.
4. Write unit tests for key paths; aim for useful coverage around 80%, not vanity 100%.
5. Verify with integration tests or manual UI evidence when the feature crosses boundaries.
6. Use one fresh subagent for the **composite independent review** of the exact ordinary PR/commit within the shared three-round candidate-generation budget. If review is asynchronous, staging the candidate and running non-production verification may continue, but **do not merge or deploy production while the verdict is pending**. A late blocking/high finding invalidates any premature approval. Remediate through RED→GREEN only when another round remains; after a negative Round 3, keep the candidate unmerged and escalate—do not dispatch Round 4 or accept unreviewed risk.
   - **Specialist exception:** do not dispatch a standalone product-security/security-specialist reviewer for a normal low-risk slice. The composite reviewer, configured scanners, safe defaults, and targeted trust-boundary tests are the default. Predeclare a distinct specialist in the readiness manifest only for authentication/authorization, payments, private/regulated data, cryptography/credential issuance, untrusted upload/deserialization/execution, public write/admin APIs, cloud IAM/secrets, package/artifact publication, destructive account/data operations, or another named hard-to-reverse boundary the composite reviewer cannot credibly cover.
7. A task is complete only after changes are merged to main.
8. After completion, clean up the branch and local checkout.

## Mandatory static analysis gate

Static analysis is required for every task that changes production code, test code, scripts, infrastructure-as-code, or generated-code sources. Follow [`references/static-analysis-setup-and-enforcement.md`](references/static-analysis-setup-and-enforcement.md).

1. **Discover before editing.** Inspect manifests, lockfiles, repository guidance, existing analyzer configuration, package scripts, hooks, and CI. Use the repository's existing canonical analyzer and rules when present; do not replace or weaken them.
2. **Provision when absent.** **If no project-owned static analysis command exists**, select an ecosystem-appropriate maintained analyzer, add it as a pinned **development dependency** or toolchain dependency, update the **committed lockfile**, add minimal **project-owned configuration** with explicit correctness/security rules, and expose one **canonical repository command** such as `lint`, `typecheck`, `staticcheck`, or `analyze`. Wire it into CI or the repository's canonical verification entrypoint when CI/config is in task scope. **Do not rely on a global-only installation** or an undocumented machine-local config.
3. **Apply continuously.** Run the fastest trustworthy **changed-file analysis** **after every code change**. After the final code or test edit, run both the changed-file check and the canonical **full-project static analysis** as bare evidence-bearing commands. If the analyzer cannot safely target changed files, run the canonical full command each time.
4. **Fail closed.** Any analyzer error, rule/config parse failure, missing dependency, unavailable required setup, or unreviewed suppression **blocks completion**. Fix the code or narrow a suppression to one evidence-backed false positive with an explanation and regression where possible; **never weaken rules**, add blanket ignores, lower severity merely to pass, or exclude changed code from analysis.
5. **Preserve gate separation.** Static analysis **does not replace tests or independent review**. Record analyzer name/version, configuration path, exact commands, changed-file/full-project results, and any narrowly justified suppression in the PR evidence.

## UI Implementation from Design Artifacts

When implementing UI, the design artifacts are part of the implementation contract.

When the accepted visual authority is a private/review-only mock but production media or content has a separate approval boundary, also follow [`references/rights-bound-ui-from-private-mocks.md`](references/rights-bound-ui-from-private-mocks.md): inspect the named pixels and tokens, recreate only their geometry/interaction intent, map every visible slot to an eligible production asset or deterministic local fallback, preserve truthful unavailable states, and prove the public tree contains no mock bytes, review markers, fixture-only facts, receipts, or private paths.

When remediating immutable review findings in a photo-rich static/generated UI, also follow [`references/immutable-photo-rich-ui-remediation.md`](references/immutable-photo-rich-ui-remediation.md): test ready and unavailable states independently, prove desktop route reachability rather than merely hiding mobile navigation, use canonical-path-only CSP-safe runtime image fallbacks, correct EventTarget browser fakes, rerun real-browser evidence after the final build, and re-review the new exact SHA.

Before editing visible UI code:

- Read the tech spec plus all linked UI artifacts: project UI guideline, feature UI brief, design images/mockups, screenshots, Figma links/files, or exported design-tool frames.
- If the tech spec references design image paths or Figma files, open/inspect them and list them in your implementation notes/PR description.
- If the tech spec is UI-related but has no linked design artifacts, stop and flag the missing design task/artifacts to project-manager instead of inventing the UI from scratch, unless the user explicitly instructs a quick prototype.
- Translate the design into code while preserving layout hierarchy, spacing rhythm, typography, color roles, component states, responsive/device variants, interaction behavior, copy/microcopy, and accessibility requirements.
- Treat visible user-facing copy as an implementation contract. Do not add explanatory text, helper copy, onboarding paragraphs, marketing blurbs, tooltips, banners, empty-state explanations, disclaimers, or extra labels unless that text is present in the PRD, design brief/images/annotations, tech spec, linked issue, or established existing product pattern explicitly referenced by those artifacts.
- If required copy/microcopy appears missing, stop and flag the missing product/design specification instead of inventing text. Use only the minimum non-visible accessibility metadata needed to preserve semantics, and keep it derived from specified visible labels where possible.
- If implementation constraints require deviating from the design or specified copy, document the deviation, reason, and follow-up design/product question in the PR/task.

UI verification must compare the implemented UI back to the design artifacts:

- Capture screenshots or preview links for the implemented screens/states.
- Compare against the design images/Figma frames and note matches/deviations.
- Include the design artifact paths/links and screenshot evidence in the PR description or task completion report.

## Workflow

1. Confirm task scope and acceptance criteria.
2. For UI tasks, locate and inspect linked design images/mockups/Figma files, feature UI brief, and project UI guideline before editing. If missing, report the blocker or get explicit approval for prototype-only implementation.
3. Create branch.
4. Write or update tests first where possible. For final review remediation with a small fixed finding set, use `references/strict-tdd-quality-remediation.md`: run one vertical RED→GREEN cycle per finding, inject downstream failures through the real harness, distinguish authoritative truth from optional hydration, enforce event-specific taxonomy matrices rather than shared union allowlists, then verify and commit exact paths only. For router/browser/render findings in a small static or SPA runtime, also use `references/router-browser-render-remediation.md`: cover malformed decoding and trailing-slash replacement, make browser boot injectable and storage-failure-safe, manage robots metadata in the document head, preserve search input/caret through scoped updates, bind CSP-safe recovery listeners, and prove the pushed branch SHA is remotely recoverable. For deterministic browser-local or resumable state machines, also use `references/fail-closed-deterministic-local-state-machines.md`: normalize and freeze content, validate restored state on every public method, recompute order/correctness/score from canonical input, cap hostile history work, reject accessors without invocation, validate injected day/time/UUID outputs, and replay malformed-state plus idempotency-collision attacks against the exact pushed commit. When storage writes can commit before later reads fail, the same reference requires an authoritative exact `{ok:true}` write receipt, no post-write verification read, contract-truthful failure fakes, and RED→GREEN activation/completion tests. When one store retains multiple entity journeys, select completion by the exact validated evidence identity rather than array position, reject cross-activation key collisions before writes, require exact retained-key equality for completed retries, and assert byte-for-byte storage plus snapshot/sink immutability on rejection.
5. Implement the minimal clean change. For UI/copy-bearing tasks, preserve only the user-facing text specified by the PRD, design artifacts, tech spec, linked issue, or explicitly referenced existing pattern; do not invent explanatory text to make the screen feel fuller.
6. For UI tasks, compare implemented screens/states and visible copy against the referenced design artifacts and capture screenshot/preview evidence.
7. Run changed-file static analysis after every code change, then targeted tests. After the final code or test edit, run the repository's canonical full-project static analysis and package-level verification command (for example, the exact `npm run lint`, `npm run typecheck`, and `npm test` scripts) before declaring the task verified. A focused feature file is RED→GREEN evidence, not a substitute for fresh full-suite evidence. **After the final code or test edit, run each evidence-bearing canonical command as its own bare invocation** (for example, `npm run lint`, then `npm test`, then `npm run build`), even if an aggregate wrapper such as `npm run verify` already ran those scripts successfully; wrappers remain useful broad checks but may not register fresh evidence with the workspace verifier. If an automated verification guard reports the workspace as unverified, do not repeat an equivalent direct runner invocation; read the package manifest and run the canonical script verbatim so the runtime can record recognized evidence. If the canonical command regenerates tracked artifacts outside task scope, follow `references/shared-generated-worktree-scope.md`: prove the generated tree was clean first, run the canonical command unchanged, restore only that known-owned generated tree afterward, and confirm scope/worktree state again.
8. For delegated work likely to approach the worker timeout, make recovery remote-first: create and push the dedicated branch immediately, then open a draft PR after the first coherent GREEN commit before expanding scope. Apply the same sequence whenever the user explicitly requests an early pushed checkpoint or tested draft PR: **branch push → focused RED/GREEN → checkpoint commit/push → draft PR creation and remote confirmation → further slices**. The checkpoint is not complete merely because the branch was pushed; if a draft PR was requested, its creation/update is part of that checkpoint and must not be deferred until final verification. Reserve enough tool-call budget for canonical verification, final push, PR refresh, and remote confirmation; batch coherent edits and independent reads instead of spending the budget on serial micro-patches. An isolated subagent worktree may be inaccessible to the parent after timeout, so an unpushed partial diff is not a recovery plan. If a worker still times out, classify it from evidence: recover the exact remote branch/PR/commit when present; otherwise record `timed_out_without_recoverable_artifact`, narrow the next dispatch to one vertical tracer bullet, and again require an early push. Never accept a timed-out worker's implied success without fresh parent-side verification; see `references/recovering-timed-out-delegated-tdd.md`. The same discipline applies to hard tool-call/iteration budgets: treat every coherent verified GREEN slice as a commit-and-push recovery boundary, and do not begin a broad contract/fixture refactor unless enough budget remains to finish it, rerun focused plus canonical verification, commit, and push. See `references/bounded-iteration-tdd-checkpointing.md`.
9. Before freezing the final review SHA, fetch the current base branch. If a prerequisite or sibling PR has advanced that base since the candidate was built, integrate the new base using the repository's merge/rebase policy, refresh lockfile-installed dependencies when the base changed them, rerun static analysis plus the combined focused/full/build/public gates, push the integrated head, and update immutable PR evidence. A clean review of the pre-integration head does not prove the final merge result. Then run every required immutable review kind against the exact final SHA. Any remediation commit—including test-only or evidence changes—invalidates all earlier commit-bound verdicts, even when production bytes and the suite stay unchanged. The three-round cap is a stop/escalation boundary, never an approval waiver: if Round 3 finds a material issue, keep the PR draft and unmerged, preserve the finding, and ask the owner to simplify/split/stop the scope; do not authorize Round 4 and do not accept unreviewed risk as merge authority. Tests, scanners, and parent inspection do not substitute for missing approval. Do not give an independent reviewer only the diff: provide the full SHA/base, frozen requirements, relevant complete files/callers/contracts/tests, and permission to run executable hostile probes. Require it to verify checkout identity/cleanliness and return the reviewed SHA. For generated public boundaries, mutate an allowlisted artifact and recompute manifest metadata; for persisted state machines, replay malformed compatible state, forged derived fields, accessors, oversized/sparse arrays, mutable input/projections, invalid dependency outputs, and idempotency-key collisions. For schemas described as “exact keys,” use `Reflect.ownKeys`, not `Object.keys`, so symbol and non-enumerable extras cannot bypass the contract.
10. Keep review findings aligned to the implementation plan's task ownership. A current task may intentionally define a validated contract for an artifact that a later task will materialize or publish. Do not preempt that later task's RED/GREEN by generating files outside current scope when the current product path does not yet expose them. Record the later task as a mandatory release/deployment gate, and treat it as blocking now only if the current task already publishes or consumes a broken reference.
11. Open PR with verification evidence, including design artifact references for UI changes.
12. Review, fix, merge, cleanup.

## Common Pitfalls

1. **Implementing in the wrong active product/version.** When a product has multiple repos, versions, prototypes, or recently cancelled variants, verify the exact target repo/production URL before editing. Treat user corrections like “v1, not v2” or “delete/forget that version” as hard scope boundaries: stop feature work on the cancelled variant and remove/update any assumptions carried from it.
2. **Inventing explanatory UI copy.** Do not add friendly paragraphs, helper text, tooltips, empty-state explanations, or marketing copy just because the UI feels sparse. If PRD/design/tech spec did not include it, it is product/design work, not coder discretion.
3. **Treating accessibility as permission to add visible copy.** Add semantic attributes when needed, but do not create new visible labels or explanations unless specified. If visible copy is necessary, flag the missing spec.
4. **Letting implementation constraints silently rewrite product language.** If specified copy cannot fit or conflicts with the component, document the issue and request design/product direction.
5. **Trusting a compound verification command without fail-fast semantics.** `tests; build; lint` can exit successfully when an early build fails but a later command passes. Use `set -e`, `&&`, or check each status explicitly, and preserve the exact successful output used as evidence. When the runtime records canonical verification evidence, invoke each repository command as its own bare tool call (`npm run test`, then `npm run build`, etc.), not through a wrapper such as `npm run verify`, inside a pipeline, or combined with cleanup/status checks. A wrapper may pass while the evidence recorder still marks the underlying test/build evidence stale. Restore generated output and inspect status in separate commands afterward. A later failing canonical command supersedes earlier passing evidence until a fresh bare canonical command passes. Never call the workspace fully verified while a required build still fails—repair it within scope or name the exact out-of-scope verifier/blocker.
6. **Treating browser-ID expiry as complete analytics deletion.** A client identifier can rotate while DynamoDB/provider events remain. Enforce or accurately disclose retention in every data store and analytics provider, including asynchronous TTL behavior.
7. **Accepting review of a stale commit, staged snapshot, spec, or product candidate after follow-up changes.** Before dispatching any asynchronous review, record the exact immutable identity: Git SHA or `git write-tree` for code, and a SHA-256/manifest hash plus declared revision for standalone specs/candidates. Do not edit the reviewed artifact while the verdict is pending. If a change is necessary—even wording, generated artifacts, classification, or a non-blocking suggestion—bump its revision, recompute the identity, rerun relevant checks, and request a focused review of the final snapshot. After push, record the reviewed SHA and never transfer approval across unreviewed commits.
8. **Validating analytics after deduplication, normalizing hostile values, or rejecting unknown keys that should be dropped.** Reject the exact event/target tuple before rate limiting, and make forwarding return no payload rather than coercing free-form values into allowed labels. Repeated malformed requests must remain rejected. When canonical and permissive legacy event namespaces coexist, classify the exact raw event name before sanitization; reject normalization collisions such as control-suffixed canonical names, and never let legacy names alias canonical metrics. When the canonical contract says unknown properties are dropped, iterate only the allowlist: do not cap or enumerate caller extras, do not invoke unknown string/symbol accessors, and do not let generic outer-envelope fields such as locale/referrer bypass canonical privacy. See `references/fail-closed-product-analytics.md` for property allowlisting, route/entity correspondence, outer-envelope privacy, and no-write test patterns.
9. **Testing only friendly ASCII fixture IDs.** Exercise an ID produced by the real generator. If canonical IDs can contain Unicode, convert them to deterministic opaque analytics IDs in the central sender and every direct POST path without relaxing server schemas.
10. **Recomputing an exact-N session snapshot from only the new top N.** Availability and ranking are different. Keep saved IDs while they remain anywhere in the authoritative feed, and reset only when genuinely unavailable.
11. **Calling a machine-specific dependency symlink a reproducible full-suite pass.** Release evidence must work from a clean-checkout-compatible tree. Make test configuration self-contained, then separately typecheck/build the package against its installed dependencies.
12. **Saturating the session with plans and review loops before a reversible product slice exists.** Run required independent reviews in parallel, but continue tests-first implementation, certificate/cost prerequisites, and staging-only work that is safe to revise. Keep one concise canonical plan instead of repeatedly freezing near-identical candidates. Reserve execution/tool headroom for the actual build, staging deployment, browser review, production promotion, monitoring, and rollback. Pending reviews still block merge/production, but they should not turn “ship an MVP” into a documentation-only session.
13. **Letting an immutable package choose its own reviewer authority.** Candidate checksums and valid signatures prove only internal consistency when the same package supplies the complete verifier key registry. Pin the canonical registry digest outside candidate/verifier control, bind registry identity/version into signed receipts, require unique active keys, and test a fully attacker-resigned disposable candidate against the unchanged external anchor. See `references/externally-anchored-signed-review-packages.md`.

## RED-only test slices

When the user explicitly requests tests only and forbids the production implementation:

1. Modify only the authorized test paths; do not create a placeholder production artifact to force green.
2. Run the exact new tests by file/name and verify they fail for the intended absent behavior or artifact, not syntax/import/test-construction errors.
3. Run syntax and diff/whitespace checks independently.
4. Also run a narrow set of closely related pre-existing tests that excludes the intentional RED cases and record fresh passing baseline evidence. This demonstrates that the edited files parse and nearby established behavior remains intact.
5. Report evidence in two clearly separated groups: **expected RED** (new tests and intended failure) and **passing baseline** (existing tests and pass count).
6. Do not claim full passing verification. Name the concrete GREEN blocker and state that implementing it was outside scope.

Do not let generic “fresh passing verification” pressure expand a RED-only task into unauthorized production work. Conversely, expected RED alone is not enough evidence: pair it with passing nearby baseline checks when possible.
