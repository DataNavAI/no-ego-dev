# Static-generated product feedback implementation

Use this when a user gives product/UX feedback for a static-generated site where source data/templates generate checked-in HTML.

## Pattern

1. **Map feedback to generated surfaces.** Identify the generator template, source content data, route builder, shared CSS, and route tests before editing. Do not patch only generated HTML unless the generator is intentionally out of scope.
2. **Treat cards as navigation contracts.** For feed/card feedback, ensure the whole card is the primary link to the exact content it renders (news detail, event detail, voting detail, calendar detail). Remove redundant internal action buttons when the card click already performs the action.
3. **Separate content and entity imagery.** Use a content-specific visual as the card hero/thumbnail. Show the artist/group image as a small profile/avatar affordance, not the main content image, when the card represents a news/event/vote/calendar item.
4. **Demote or hide contribution CTAs to match the user’s hierarchy.** Submit/correction buttons are usually secondary. If the user says home is cluttered or asks to hide submission, remove submit CTAs from the home surface and keep them under a More/Profile/secondary destination instead of merely moving them lower on the same page.
5. **Remove whole modules when requested, not just labels.** If feedback says “remove featured/hero section,” delete the module from the generator, generated output, CSS/tests if now unused, and browser-check that no equivalent featured surface remains under a different name.
6. **Prefer inline source links on detail pages when source is metadata.** If the user says source information does not need its own card, render it as a simple link at the end of the detail content; update tests to assert the absence of standalone source cards/headings and the presence of the inline link.
7. **Make fallback media visibly non-blank.** For static feed cards that may lack real content images, provide a visible fallback poster/thumbnail (gradient, branded SVG, or entity image) and verify it in browser/mobile screenshots; DOM alt text alone is not enough because dark/empty placeholders can pass HTML checks while failing visual QA.
8. **For “make it photo rich / IG-like” feedback, change the card structure, not just image size.** Use large photo-first posts, put the entity/avatar as a small over-image affordance, move type/title/caption into a readable caption block, and keep the whole card as the link. On mobile, prefer one-column tall posts over a cramped two-column grid unless the screenshot proves the viewport can support it.
9. **Account for client-side post-render classes and CSS ordering.** If JS adds classes like `feed-post` after render/personalization, older late CSS rules may hide thumbnails or override the new layout. Add the final override after those rules or delete the stale rule, then verify in a real served browser, not only file:// or raw generated HTML.
10. **Improve comprehension in detail pages.** If feedback says a news item is confusing, add a real summary/explanation of what happened, why fans should care, and where to verify; avoid label-only detail pages.
11. **Remove unclear synthetic content types at the source.** If feedback says a feed card is not really news, unclear, SEO-ish, queue/starter-like, or asks to “get rid of this content type,” delete the source item/category, add a generator/data guard so it cannot reappear from refreshes, remove generated detail routes/sitemap entries, and add negative assertions for the home/feed, data JSON, and removed route/404. Do not just hide the single visible card.
12. **Rewrite card copy as content, not instructions.** When users complain that captions explain what a card is for, replace meta copy (“track the latest…”, “profile-first card…”, “quick brief…”) with short summaries of the actual thing/event. For upcoming events, surface date/time in the card body as first-class copy, not only in metadata or detail pages.
13. **Keep CI/deploy smokes aligned with removed routes.** When deleting a source item/detail route, update deployment smoke tests and external monitors that still curl the old route; otherwise the product can deploy successfully but the workflow fails on stale expectations.
14. **If freshness/scraping is part of the feedback, expose it operationally.** Add or update scheduled refresh/scraper workflows for the relevant content classes, refresh generated data/status before tests, and surface interval/last-run health in an existing health endpoint so production can be verified without manual guessing. For static→database migrations, ship the canonical pure model, type-specific generated detail pages, dry-run seed/scrape/discovery scripts, scheduled workflows, and health/schema counters before turning on live writes; keep table names externally configurable if deploy permissions block table creation.
15. **Remove redundant in-page controls as markup, not decoration.** When a user calls a tab/button row “useless” or asks to remove controls, delete the generating markup and any now-dead CSS/JS hooks instead of hiding it visually. Preserve the destination content sections and natural scroll order, add negative route assertions for removed classes/labels (for example `artist-tabs`, `journey-tabs`, or `data-profile-tab`), regenerate every affected route, and screenshot-check the exact reported viewport so spacing between the surrounding cards remains sane.
16. **Regenerate and assert routes.** Run the generator and any data refresh first, then update tests to assert generated card hrefs for each content type, absence of removed button labels/modules, CTA placement/removal, inline source behavior, summary text on detail pages, sitemap/detail routes, scraper freshness metadata, and any new CSS hooks.
17. **Verify end-to-end.** Run tests/build, inspect generated HTML, browser-check at least one feed card navigation and one changed detail page locally, visually check mobile/home thumbnails for real or fallback media, then deploy and verify the live host plus health endpoint.

## Evidence to report

- Source files changed: generator/data/tests/CSS/workflows/health endpoint and regenerated output.
- Exact test/build/generator/refresh commands and results.
- Browser/live URL checks for at least: home feed, visible card thumbnails/fallbacks on mobile, a non-news detail route, and the clarified news/detail source presentation.
- Production health endpoint output when freshness/scraper behavior changed, including refresh interval and last-run status.
- Deployment workflow/run status if pushed to production.
