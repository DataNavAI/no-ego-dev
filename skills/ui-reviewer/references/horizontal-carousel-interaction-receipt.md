# Horizontal carousel interaction receipt

Use when a responsive carousel is release-bearing. Screenshots complement but never replace runtime interaction evidence.

## Candidate binding

Freeze an exact commit/tree, serve only those bytes from a reviewer-owned port or exact image, and record candidate identity, route, browser, locale, viewport/device, and console/page errors. Use production-shaped data; label fixture/API limitations and repeat final proof against built/deployed output when required.

## Geometry and interactions

At each supported viewport record carousel rectangle, initial `scrollLeft`, first/second card rectangles, card/shortcut counts, and visible-next width from rectangle intersection. Capture an element screenshot from the same run.

Exercise:

1. initial counter/selected shortcut;
2. second shortcut, then wait for scroll settling and assert counter, selection, and aligned card;
3. keyboard forward and counter advance;
4. reverse/reset;
5. article/action link URL, target, rel, and accessible destination name; and
6. zero feature-specific exceptions or console errors.

Never compare page-relative `offsetLeft` directly to scroller-relative `scrollLeft`. Normalize offsets against the first card or compare card/scroller rectangles. Include a regression case where the scroller has a non-zero page-relative origin.

The receipt includes exact identity, tests/build, desktop/mobile geometry, transition sequence, link contract, screenshots, and console status. Repeat after deployment; pre-deploy proof is not production delivery.
