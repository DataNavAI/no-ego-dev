# Connect a provider identity in NED

1. Respect the active profile's credential policy. If it requires guarded IFA for this provider, use the existing identity-for-agent skill and the active profile's guard. Never import or bypass those credentials. Provider connections are available in private native NEDCOM. An owner-authorized Hub standalone instance supports GitHub and AWS.
2. Check `ned identity --help` first and use the same release as the running COM. For an authorized source checkout, `node /absolute/path/to/no-ego-dev/bin/ned.js identity …` is the development entry point. Check `ned identity status <provider>`. Ask which account, role, or domain should be used if it is unclear. If an existing connection matches, use it for the requested operation and verify any additional permission required by that operation.
3. As soon as authorization is needed, call the Hermes `ned` tool with `{"action":"request_provider_auth","provider":"aws"}`, substituting the supported provider. On success, ask the user to open the **Review connection** card. The modal collects provider details and guides sign-in. The tool only queues the request. If it is unavailable, direct the user to the supported manual Provider connections screen or explain that the instance lacks this capability. Keep approval links, sign-in codes, and credentials out of Chat.
4. Explain the one applicable flow. Sign-in codes belong only on the provider’s sign-in page. Keep codes and tokens out of chat and tool output.
   - **GitHub** — NED wraps official `gh auth login --web` in an isolated per-attempt CLI configuration. Use the GitHub card/modal, enter the intended username, get the code privately, open GitHub, approve, and check approval. NED verifies the returned account with `gh api user`; compare it before confirming storage. No separate GitHub App/client ID is required for this default CLI flow. Do not run bare `gh auth login` in an agent terminal or expose its device prompt in chat. A missing gh executable or unavailable runtime is a GitHub-specific failure, not a reason to show AWS. An explicitly configured legacy App flow may still be used by an older release; follow actual reported capabilities without inventing setup.
   - **AWS** — Enter the Identity Center access portal URL and region, plus the exact assigned account ID and role. Sign in at the AWS link, check approval, and confirm the displayed account and role. Existing AWS CLI credentials are separate.
   - **GoDaddy** — Create a scoped Domains v3 personal access token on GoDaddy, then enter it and the managed domain in the private connection form. Verify domain access and confirm. Ask only for the domain in chat if needed. Enter the token only in that private form.
5. Read back `ned identity status <provider>`. Continue only after it shows the intended connected identity. A mismatch, expiry, cancel, or failed check leaves the request unfinished. Use the connection card or its recovery action first. Use private Settings only as the supported fallback. For a local disconnect the provider grants remain subject to upstream revocation.

For authorized work, use `ned identity exec github -- gh api user` or `ned identity exec aws -- aws sts get-caller-identity`. Use `ned identity domain` for read-only GoDaddy domain verification. Check capabilities separately where applicable. Never use a bare provider command as fallback or print/export stored credentials. For unsupported hosted/public transport and GoDaddy in standalone containers, report the actual capability limitation. Never substitute another provider. When several providers are needed, request and describe each separately; one successful provider does not establish access to another.
