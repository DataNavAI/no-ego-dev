Credentials, revocation, and destroy

Credential boundaries

  • ChatGPT OAuth: refresh credentials stay local. Only the current short-lived runtime credential is synchronized to its installation-owned Daytona Secret.
  • Telegram: the token enters the NED process through hidden TTY input or macOS Keychain service no-ego-dev/telegram, account TELEGRAM_BOT_TOKEN. NED validates it in-process, retains it only in controller memory for the active lifecycle, and passes it to gateway child processes only through the Daytona SDK environment map. It is never stored in a Daytona Secret, file, URL, command, log, or local state.
  • Daytona: the local launcher reads the Daytona credential from its named Keychain item or protected local file. It is not uploaded as a Sandbox Secret.

Revoke a Telegram bot token

  1. Open BotFather.
  2. Use /revoke and select only the disposable NED bot.
  3. Run ned destroy --yes to delete the exact Sandbox and model Secret.
  4. On macOS, remove the test-only Keychain item: security delete-generic-password -s no-ego-dev/telegram -a TELEGRAM_BOT_TOKEN.

Destroy and verify

ned destroy --yes

Destroy waits for deletion, then directly reads back the exact Sandbox and model Secret. Local ownership state is cleared only after remote absence is proven. Repeating destroy is safe.

Troubleshooting

  1. Token rejected: do not retry it in a command. Revoke it, create a new disposable bot, and use hidden input.
  2. Gateway disconnected: run ned doctor, then ned repair.
  3. Bot receives messages but does not answer: send hello, approve the fresh owner code with ned pair <code>, then retry.
  4. Cleanup blocked: keep local ownership state and retry ned destroy --yes. Never delete unrelated Daytona or Telegram resources.
If a token appears in chat, shell history, logs, analytics, screenshots, source, a fixture, or a URL, treat it as disclosed and revoke it immediately.
