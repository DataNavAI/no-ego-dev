# Feature: Web app previews

Status: draft — design proposal, not implemented or an approved runtime contract.
Related issues: [design #155](https://github.com/DataNavAI/no-ego-dev/issues/155); prior [single configured preview #116](https://github.com/DataNavAI/no-ego-dev/issues/116); planned [agent/COM implementation #157](https://github.com/DataNavAI/no-ego-dev/issues/157) and [Hub capability #81](https://github.com/DataNavAI/ned-hub/issues/81).
Revision: preview-design-r2. Decision owner: project user. UI direction: pending selection; A recommended. PR mode: MERGEABLE documentation proposal, not runtime release authority.

## User outcome and scope

Users see and interact with the working web app Hermes is building on their NED instance, without copying localhost URLs or opening firewall ports. Hermes owns starting and stopping app processes; it explicitly registers a running local HTTP listener. NED owns the registry, connectivity and private preview access. Multiple apps can coexist and be selected.

One primary journey: **CUJ-001 run → register → view**. Supporting journeys: **CUJ-002 switch apps** and **CUJ-003 recover or remove**. Both local desktop and authenticated Hub desktop/mobile access are intended for the first usable release; the feature is not complete if remote browsers receive the instance's localhost URL.

Must ship: registration/list/removal through CLI and native tool; project-aware app selection; isolated embedded app and Open in new tab; HTTP/assets/forms and WebSocket/HMR forwarding; readiness, stopped, reconnecting and unavailable states; authentication and stale-route revocation. Reuse COM's existing shell, project registry, selected agent home and Hub connection.

Manual/internal: Hermes configures dev-server host/HMR/embedding settings and manages process lifetime. Parking lot/non-goals: production deployment, arbitrary remote URLs/TCP forwarding, automatic port scanning, NED starting/stopping/restarting arbitrary commands, public anonymous sharing, screenshots/DOM control of app content, split-screen previews, framework-independent source/HTML rewriting, automatic OAuth fixes, native apps and cross-container/network-namespace forwarding.

Current implementation supports only one project `.nedcom.json` loopback URL, checked by HEAD and opened in a new tab. It does not implement this proposal. [Technical design](TECHNICAL_DESIGN.md) records inspected code, reuse and cross-repository gaps. [Visual review](design/DESIGN_REVIEW.md) provides runnable alternatives and the selection decision. Existing [device registry](../../../.projects/no-ego-dev/product/supported-device-interfaces.yaml) is historical and needs release-specific reconciliation before runtime support is claimed.

## Requirements

- FR-001: `ned preview register <slot> --port <integer> --name <label> --project <path> --json` registers one verified app in the selected agent/profile. Native `ned` action `register_preview` uses the same service. Names are nonempty printable text of1–80characters, excluding control characters; slots match `[a-z][a-z0-9-]{0,39}`. Only local IPv4 HTTP listeners on127.0.0.1, ports1024–65535, are allowed. Reject URLs, commands, credentials, wildcard listeners, other network namespaces, configured COM/gateway/Hub/relay/admin ports and listeners outside the selected project/process ownership. An unverifiable listener fails closed; no automatic scan or guessing.
- FR-002: Reuse registered projects and their IDs; registration can idempotently establish project metadata without creating goals/tasks. Persist preview metadata in the selected NED DB, partitioned by a durable agent-home instance ID even when an explicit DB override shares a file. No project-local config rewrite or legacy data migration. Foreign agent-home records never appear merely because a shared project/DB exists.
- FR-003: Stable logical identity is `(runtime_instance_id,project_id,slot)`. Same listener identity and same metadata registration returns the same app ID/generation; a changed listener or metadata creates a new generation and invalidates old access/streams. Concurrent same-slot writes use expected generation/compare-and-swap; a stale updater receives409. A lost reply is reconciled with list/get before retry, not a duplicate app. Native results return metadata only, never bearer grants or commands.
- FR-004: Capture and validate OS user, listening PID, process start identity and canonical project working directory. Revalidate before and after upstream connection establishment, before forwarding bytes, and every2seconds while forwarding. PID reuse or port reuse by another process makes the app unavailable and closes streams; do not silently expose the replacement service. Hermes must explicitly re-register a restarted app. Registration persists after COM restart, but no route serves until reverified. Registration does not keep a process alive. The supported Hermes process mechanism must keep the server running after the launching command and agent reply complete; proving that lifecycle is part of runtime acceptance, otherwise report an unavailable prerequisite.
- FR-005: UI lists all registered apps in this instance, grouped by project, including stopped apps with text status. Selecting an app in another project atomically selects that project in existing workspace controls; chat/session/draft remain intact. A global project change restores the last app for that project, otherwise first running app sorted by name then opaque ID; with one app select it automatically. Persist only opaque selected IDs per browser, never grants/ports/paths or secret data. Removed selections clear; stopped selections stay selected instead of silently switching.
- FR-006: Preview toolbar contains the selected app, project identity, text state, Reload and Open in new tab. Selection is the only user action required after registration; no port entry. Desktop shows the existing chat/preview layout; mobile uses the existing Chat/Preview navigation and a full-width app surface. Final menu-versus-tabs direction is DEC-01, pending owner selection. Native keyboard/focus,44px touch controls,320px reflow and no unintended horizontal page overflow are required.
- FR-007: Every app generation has a separate origin from COM, Hub control and other apps. Never mount executable app content under COM's origin or expose COM APIs on an app origin. Remote origins use a configured dedicated preview namespace and authenticated Hub relay, not public random links. Local embedding requires a proven compatible COM/app schemeful-site and cookie arrangement as an output of the origin/auth spike. The current127.0.0.1 COM plus sibling .localhost apps with Strict cookies is explicitly not a working contract; candidate local aliases and required Host/origin migration are in the technical design. Remote control-plane auth must meet the host-only __Host-cookie migration gate in TECHNICAL_DESIGN.md before enabling same-site sibling app origins. App ports remain private; no inbound app-port firewall changes.
- FR-008: Authorize the current Hub user for the exact instance/app/generation on bootstrap, HTTP and WS admission. Use a one-use30second bootstrap grant in a POST body, then a host-only HttpOnly Secure preview access cookie for remote HTTPS; local cookie policy is an unresolved output of the explicit compatible-site spike, not a claimed working HTTP configuration; no bearer in URL, persistent browser storage, tool response, app payload/server request or logs. A one-use grant may exist briefly in trusted COM memory and a form input, disposed immediately after submission; never expose it to app DOM or a worker. Local-loopback bootstrap requires a proven compatible site/cookie arrangement and validated COM Origin; it must not silently weaken cookies to repair a cross-site tuple. Bootstrap form requests are a separate narrow request class from header-protected COM JSON APIs. Preview sessions expire after15minutes; COM can renew while authorized. Logout, instance token revocation, disconnect, unregister or generation change revokes grants and closes active streams within5seconds. Fail closed on control-plane uncertainty.
- FR-009: Forward HTTP paths at the app origin root, streaming bodies/responses and supporting WebSocket upgrade/binary frames/backpressure for HMR. Strip NED/Hub credentials and trusted routing headers before the app; do not forward control-plane bearer credentials. Allow the app's own authorization/cookies within its origin; strip reserved NED cookie names and reject Domain attributes in upstream Set-Cookie. App JavaScript can still set parent-Domain cookies; DOM/web-storage and NED authority isolation do not imply arbitrary application-cookie isolation. Remote NED auth requires host-only Secure __Host-prefixed cookies. Cookie-authenticated apps are supported only with a tested host-only Secure __Host-prefixed auth-cookie contract; unprefixed/Domain-cookie authentication is unsupported for this release. Never follow upstream redirects server-side; rewrite same-target loopback Location to the assigned app origin, allow relative Location, reject other private/loopback redirect destinations and do not strip app CSP/X-Frame-Options. COM response CSP admits only the fixed configured preview namespace (for example https://*.preview.example.test), not a dynamically selected-only origin and not a global wildcard. Actual app access remains exact ID/generation/user-authorized at ingress, and the UI validates the returned origin against that namespace. A namespace change requires explicit document refresh; app selection/re-registration within it does not. No app-origin CORS permission on COM.
- FR-010: Health distinguishes verified HTTP service availability from app rendering. A valid HTTP response, including401/403/404/405, is not a stopped process;5xx is an app error. Do not rely solely on HEAD2xx, iframe load or opaque cross-origin DOM inspection to claim the app rendered correctly. Preserve app security headers; detectable embedding denial shows Open in new tab. Unknown framing/browser failures keep a usable Open in new tab action and connection Retry. Retry reconnects/rechecks and never starts an app. First-release preview origins prohibit service, shared and dedicated workers through an enforced worker-src 'none' policy and worker-script ingress denial, in frame and top-level views. Origins must be fresh and never reused; worker/PWA-dependent apps are unsupported rather than receiving a weaker bootstrap boundary. HMR must infer its host from the current origin without restart-bound fixed-host configuration; incompatible configurations remain unsupported pending a proven allocation lifecycle.
- FR-011: `list/get` returns registration and observed states; `unregister <id> --expected-generation <n>` removes routing only, is idempotent at that exact generation, does not kill the app process, and cannot remove a newer generation. A removed route is never reused for another app. Stop/build/restart belongs to Hermes; agent guidance must not equate registration with deployment or process supervision.
- FR-012: Bound resources:20 registrations per instance; preview traffic at most32 HTTP channels and16 WS channels,8HTTP/4WS per app, retaining at least16 of the existing64 shared relay channels for COM. Headers32KiB, streamed request body32MiB, connect timeout5seconds, HTTP response inactivity120seconds, WS heartbeat30seconds. Saturation gives429/503 without starving COM. No response-body buffering or app bodies/headers/query strings in NED logs.
- FR-013: Keep existing `.nedcom.json` Open app behavior until explicit migration. When new registrations exist for a project, they take precedence in the new selector; never auto-tunnel legacy URLs or silently register a loopback service. Feature-disabled/old-client negotiation retains current COM-only behavior. Hub rollout and local-instance rollout are separate required gates.
- FR-014: Reuse opt-in NED telemetry and sanitized local aggregate diagnostics, without a new analytics provider. Proposed events: `preview.register.result`, `preview.connection.result`, `preview.select`, with only version, bounded result code, local/Hub mode and duration bucket. No names, raw IDs, project paths, ports, URLs, user input, query strings, cookies or tokens. Telemetry remains off by default. Daily launch-period review uses aggregate connection success/latency, wrong-app/stale-route incidents and issue feedback; no raw browser-navigation tracking.

## Critical user journeys

### CUJ-001: Run, register and view the working app
Actor: Hermes then authorized user. Primary value journey. Start: selected NED profile, known project, no registered app. Prerequisites: supported local listener identity adapter; local relay, or authorized Hub with preview protocol/DNS/TLS enabled. Hermes runs a loopback dev server, waits for a real HTTP response, registers its slot/port and reads persisted metadata. COM discovers registration, selects the sole app and embeds its issued origin. User can interact with app assets/forms and HMR. Success is the correct fixture's visible app and a live reload update; registration success alone is insufficient. Invalid listener/auth/tunnel errors publish no usable unauthorized route and show recoverable state. Registration from Codex must not appear in Hermes by default.

### CUJ-002: Switch between multiple running apps
Actor: user. Necessary when Hermes runs storefront/admin/docs concurrently. Start: two apps in one project, one in another; one stopped record. User selects another app through DEC-01's control. Within the same project only the preview changes. Across projects the project control changes atomically; stale list/health/iframe/bootstrap responses cannot replace the new selection. Chat draft and conversation are preserved. Success: correct app identity/content, isolated DOM/web-storage and NED routing authority; the supported prefixed-cookie auth fixture also remains independent, keyboard/touch focus retained. Restore opaque selection on reload after validating current membership; otherwise use FR-005's deterministic fallback.

### CUJ-003: Recover or remove a preview
Actor: Hermes and user. Necessary for a working development loop. Start: selected app stops, reconnects, restarts or is removed while UI/network operations are pending. UI keeps selection with App stopped or Reconnecting state. Retry only checks connectivity. Hermes restarts/re-registers with a new generation; old URLs/tickets/streams do not expose a new port owner. User then reopens the verified app; unregister removes the route and selection, not the process. On COM restart no old app serves before process revalidation. On logout/revocation every access path fails closed. Cleanup must not affect another preview, profile or COM itself.

## Detailed test cases

All runtime cases below are **future product acceptance procedures**, NOT RUN for this design-only revision. Planned integration/E2E automation must replace the manual designation as implementation lands; there are no pretend passing runtime tests. Current design acceptance is TC-007 only.

### TC-001: Registration, retries and profile ownership
- Journey / requirements: CUJ-001 / FR-001–004, FR-011.
- Level / automation: manual; future integration automation required before runtime release.
- Preconditions / fixtures: Implemented candidate, disposable profilesA/B and projectP; synthetic HTTP serversA:3000 andB:3001 inP, foreign projectQ:4000; inject supported listener-identity adapter. Empty registry, same explicit project DB across profiles variant.
- Given: A is running under the same OS user/project; P is not yet in project metadata.
- When: Register slot web, repeat exact command, read get/list; race two updates at the same expected generation; retry after dropping the first response; switch profile.
- Then: One project record and one preview; same-input retry retains ID/generation; one competing update wins and stale update409; B does not see A's preview despite shared DB; no goals/tasks created.
- Steps and assertions: Record exact JSON ID/generation; get it before retry. Try ports0,1023,65536,`3000;echo`, URLs, unknown slot characters,80-character name boundary, wrong UID/cwd, wildcard listeners, symlinked project, configured control port and unverified PID; reject with no new registration/route and no process execution. Race PID/start identity replacement before publication; admission fails.
- Variants / negative cases: Missing project folder, unavailable DB/OS adapter, stale generation and20-registration limit. Auth is not used to bypass local ownership. Interrupted transaction is all-or-nothing; readback on uncertain reply.
- Cleanup: Unregister only captured IDs/generations; stop synthetic servers; remove disposable stores. Verify unrelated records/processes remain.
- Pass evidence: CLI/native dispatch and reopened registry assertions; future tests must use real SQLite/process boundaries, not prose checks.

### TC-002: Local and remote app journey with HMR
- Journey / requirements: CUJ-001 / FR-006–010, FR-012.
- Level / automation: manual; future irreducible browser/tunnel integration automation required.
- Preconditions / fixtures: Two synthetic pages with unique visible app markers, root assets, nested client route, form POST, streamed response and binary WS echo/HMR. Real disposable relay and Hub auth fixture; local and remote browser modes. No real credentials.
- Given: AppA's listener is verified and registered; authorized user opens COM from a different host in remote variant.
- When: Open preview, load `/assets/main.js`, deep-link `/checkout`, submit a form, observe a file/HMR update after the launching agent reply and shell have completed, then Open in new tab.
- Then: Correct marker, assets/routes/forms and WS work through assigned app origin; no browser uses raw instance localhost remotely. New tab uses the same authorized app generation. Literal localhost HMR fallback is treated as failure, not an acceptable dev-only warning. A fixed-host-only server is a negative unsupported fixture: configuring originA then restarting/re-registering must not be claimed convergent or retried indefinitely.
- Steps and assertions: Capture host/origin/cookie headers at app sink; no NED credential/reserved routing header arrives. Verify forwarded app auth survives within origin. Exercise32MiB boundary, oversized headers, slow connect/inactivity and channel saturation; enforce FR-012 and COM remains responsive.
- Variants / negative cases:401/403/404/405/500, HEAD405, redirect relative/current-loopback/other-private destinations; preserve response security headers. Missing browser hostname resolution, wildcard DNS/TLS or protocol support is an explicit unavailable prerequisite, not a fake iframe success.
- Cleanup: Revoke fixture sessions, close channels/servers and remove synthetic DNS/cert fixture only.
- Pass evidence: Real browser + HTTP/WS boundary logs redacted; independent local and remote probes required. Planned procedures alone do not establish pass.

### TC-003: App and COM isolation
- Journey / requirements: CUJ-001, CUJ-002 / FR-007–009.
- Level / automation: manual; future security integration/browser automation required.
- Preconditions / fixtures: COM with synthetic secret sentinel, appsA/B on distinct issued origins and logged-in/out owner/foreign users. Real browser in a controlled DNS/TLS fixture; disposable signing keys.
- Given: AppA contains hostile synthetic script and can set cookies/redirect/respond with HTML.
- When: Attempt parent DOM/storage, COM `/api/secrets`, Hub control APIs, appB data, reserved/Domain-cookie injection, grant replay, expired/wrong app/wrong generation/foreign-user grant, untrusted Origin and forged target headers; repeat HTTP and WS.
- Then: No sentinel/credential read, COM action or cross-app response; no privileged origin serving app content. Consumed/expired grants fail; app payload never receives bootstrap grant; no credential in URL/history/tool/logs. COM exact-Origin/header protections continue to reject same-site sibling requests.
- Steps and assertions: Inspect browser cookies/storage/network and app sink, not only CORS headers. Logout/revoke instance while WS active; close it within5seconds and reject reconnect. Bootstrap cookie is host-only and never accepted as COM/Hub auth. Prove separate request classes: COM mint JSON with custom header/exact Origin, bounded bootstrap URL-encoded form with explicit Origin-preserving referrer policy and null-Origin rejection, app cookie HTTP and exact-Origin WS. Attempt root-scoped service-worker registration/control before renewal, including a positive non-preview control fixture; enforced worker prohibition plus fresh nonreused origins must keep grants from any worker. Try appA document.cookie with an appB auth-name Domain cookie: it must not change NED authority or the supported __Host-prefixed appB session; unprefixed app-auth noninterference is explicitly unsupported, not a passing guarantee. Dedicated preview namespace cannot be an alias of a control origin.
- Variants / negative cases: Third-party-cookie restrictions, reload/new-tab and app's own login cookie; an unavailable isolation configuration blocks preview access rather than reducing guards. Same-OS-user compromise remains outside this boundary.
- Cleanup: Revoke all fixture grants, delete browser contexts and fixture stores; sentinel never in retained evidence.
- Pass evidence: Redacted assertions from browser/Hub/agent boundaries. Cross-origin claims need real browser proof.

### TC-004: Multiple apps, mobile and stale selection
- Journey / requirements: CUJ-002 / FR-005, FR-006, FR-010.
- Level / automation: manual; future deterministic UI tests and one focused browser case required.
- Preconditions / fixtures: Implemented candidate with apps Storefront/Admin/Docs inP and Help center inQ. Docs stopped. Desktop1280×800, mobile390×844,320px reflow, keyboard and touch. Controlled delayed list/health/grant responses.
- Given: Storefront selected and chat draft present.
- When: Select Admin, rapidly select Help center before Admin's delayed reply, change project back toP, reload, stop selected app, remove selected app.
- Then: Only current selected generation navigates; cross-project selection updates project controls without changing chat/draft; reloaded membership validated; stopped selection retained, removed selection falls back per FR-005. Add newly registeredB and a new generation after the COM document loaded; its fixed namespace CSP allows the authorized navigation without a parent refresh or chat-draft loss. A changed configured namespace instead shows an explicit refresh-required state and does not silently discard the draft. Accessible label/status/focus work; no page overflow or hidden focus targets. DOM/web storage and NED authority stay distinct; cookie-auth independence is claimed only for the tested supported prefixed-cookie fixture.
- Steps and assertions: Hold and release stale responses in reversed order; assert frame teardown and latest opaque identity, not array index/title matching. Exercise longest label, empty registry, keyboard selection and mobile navigation. Reload reloads only selected iframe.
- Variants / negative cases: Selected ID removed during grant request, duplicate labels, app renamed, unsupported embedding headers and browser error. Open in new tab remains the recovery for embedding denial; never strip app CSP to pass the test.
- Cleanup: Close fixture browser/server; remove only test-owned selection state and registrations.
- Pass evidence: Acceptance map in design/ui-brief.md, executable state assertions and inspected desktop/mobile screenshots for the actual implementation.

### TC-005: Process restart, port reuse, unregister and rollback
- Journey / requirements: CUJ-003 / FR-003, FR-004, FR-008, FR-011, FR-013.
- Level / automation: manual; future process/relay integration automation required.
- Preconditions / fixtures: AppA registered, issued URL and active WS. AppB prepared to bind the same port with distinct marker. Capture initial PID/start identity, app generation and route. Disposable COM/Hub, old-client protocol fixture and legacy `.nedcom.json` project.
- Given: A is stopped after registration.
- When: Bind B to its port, retry old route, restart COM, reconnect Hub, re-register explicitly, unregister old generation while newer one exists, then disable new feature negotiation.
- Then: Old route never returns B; existing connections are revoked within5seconds; persisted record is unverified/offline until checked; explicit registration makes a new route generation; stale unregister409 cannot delete it. Exact repeated unregister succeeds without killing the process. Legacy Open app works without auto-tunneling or config writes; old Hub/client do not accept unknown preview control messages.
- Steps and assertions: Probe before/after each transition; compare app marker, process/start identity and registration readback. Drop unregister reply and retry with the same generation; no newer record removal. Rollback disables new routes and closes streams while preserving metadata and existing COM/legacy behavior. Retirement never reuses an app origin or offers an old worker a new bootstrap grant; revocation prevents new network access but does not promise erasure of downloaded app content/storage.
- Variants / negative cases: PID reuse, workspace replacement/symlink, missing listener adapter and revoked Hub credentials. No remote resource deletion or process takeover as recovery.
- Cleanup: Stop owned fixture processes and remove owned records; verify other apps/COM still work.
- Pass evidence: Process-boundary assertions, exact protocol versions and redacted revocation timings.

### TC-006: Privacy, diagnostics and learning

- Variants / negative cases: Missing telemetry sink is nonfatal; unsupported schemas fail closed. Revenue/conversion inapplicable to this developer capability. No third-party analytics provisioning.

- Pass evidence: Allowlist assertions plus project1 feedback/issue review record; no real credentials/content in evidence.

## Open questions and coverage gaps

- DEC-01: user chooses menuA versus tabsB before PRD freeze. Other recommendations are provisional architecture for independent review, not user-approved runtime decisions.
- Hub requires new preview-origin/auth/HTTP+WS capability, wildcard DNS/TLS and hosted ingress coverage. This design authorizes no cloud/DNS changes. Existing staging recovery work remains independent; do not repurpose its receipts.
- Listener identity adapters must prove project ownership on supported macOS/Linux/container platforms. Missing platform proof is a release blocker; Windows preview registration is planned/deferred, not claimed supported from task-CLI Windows tests.
- Third-party-cookie handling, local app-host resolution, embedding restrictions, real framework HMR and public authenticated isolation need technical spikes and actual browser evidence; mocks cannot certify them.
- Existing device registry and COM preview documentation must be reconciled in implementation; no runtime tests exist for this feature yet. Design completion is a reviewed draft handoff, not shipped previews.

## Feedback and measurement

Primary outcome: an authorized user reaches the correct running app after Hermes registers it. Reuse existing opt-in telemetry and local diagnostics (zero new provider cost); no new external analytics service or customer-content tracking. Report aggregate connection success/latency and failed registration causes; do not claim paint/content success without cooperative fixture/QA evidence. Repeated preview selection is supporting usage, not a new-user retention product. Conversion/revenue are inapplicable.

Feedback channel: existing project GitHub issues and direct user feedback, linked to project1. NED product owner reviews it daily during active rollout/first week, clusters wrong-app, unavailable, HMR and mobile issues and records disposition/owner/verification in linked issues.
